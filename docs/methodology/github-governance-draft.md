# GitHub 거버넌스 토론 초안

> 상태: **팀 판정 전 초안**
> 목적: 한 사람이 규칙을 확정하는 문서가 아니라, 팀이 오늘 결정할 항목을 같은 화면에 놓는 문서다.

## 1. 왜 지금 논의하는가

이번에 실제로 다음 사건이 있었다.

1. 팀원이 `docs/ideas/`에 새 문서를 Pull Request로 올렸다.
2. PR은 `main`에 merge됐고 GitHub Pages 배포도 성공했다.
3. 그러나 사이트 메뉴가 `mkdocs.yml`에 수동으로 고정돼 있어 새 문서를 메뉴에서 찾을 수 없었다.

즉 문제는 “팀원이 GitHub를 못 썼다”가 아니라, **문서 추가와 공개 사이트의 발견 가능성이 자동으로 연결되지 않은 구조**였다. 현재 PR은 자동 navigation, 배포 전 검사, 배포 후 공개 URL 검사를 해결 후보로 제안한다.

이 사건은 동시에 다음 운영 질문을 드러냈다.

- 누가 PR을 review하는가?
- review가 끝난 PR은 누가 merge하는가?
- 초기 레포 관리자가 매번 개입해야 하는가?
- Notion과 GitHub 중 어디가 최종 기록인가?
- GitHub가 처음인 팀원에게 처음부터 어떤 도구까지 요구할 것인가?

## 2. 현재 제안과 아직 확정되지 않은 것

### 사용자가 회의 출발점으로 제안하는 것

- **제안 1:** 팀의 최종 문서와 변경 이력은 GitHub `main`의 markdown을 정본으로 둔다.
- **제안 2:** `docs/` 아래 markdown은 `main`에 merge되면 Pages에 자동 게시한다.
- **제안 3:** 브랜치와 PR은 변경을 제안하고 검토하는 기본 경로로 쓴다.
- **제안 4:** 초기 관리자는 저장소 설정과 장애 복구를 맡을 수 있지만, 모든 내용 변경의 영구 승인자가 되지는 않는다.

팀은 각 제안을 그대로 채택하거나, 수정하거나, 다른 안으로 바꿀 수 있다.

### 팀이 판정해야 하는 것

- PR에 다른 팀원 1명의 승인을 필수로 할지
- 승인 뒤 작성자가 직접 merge할지, 별도 담당자가 merge할지
- 문서 변경과 코드·배포 설정 변경에 같은 규칙을 적용할지
- Notion을 읽기 전용 archive로 남길지, 회의 중 임시 메모에도 쓸지
- `docs/ideas/` 안에서 후보 아이디어·조사자료·채택안을 폴더나 metadata로 나눌지
- 위 규칙을 GitHub branch protection으로 언제부터 강제할지

## 3. 역할은 권력이 아니라 책임으로 나눈다

| 역할 | 기본 책임 | 기본적으로 하지 않는 일 |
|---|---|---|
| 작성자 | branch에서 변경하고 PR을 연다. 변경 이유와 확인 방법을 남긴다. | 자기 PR을 혼자 승인한 것으로 간주하지 않는다. |
| reviewer | 내용·영향·확인 방법을 보고 승인하거나 수정을 요청한다. | 단순히 merge 버튼을 대신 눌러주는 사람으로 축소되지 않는다. |
| 초기 maintainer | 권한, Pages, branch protection 같은 저장소 설정과 장애를 관리한다. | 모든 문서와 코드의 상시 승인자가 되지 않는다. |
| 팀 | 정본, review, merge, 도구 사용 규칙을 함께 판정한다. | 초기화자가 작성한 초안을 자동으로 확정 규칙으로 간주하지 않는다. |

## 4. merge 운영 선택지

### A. 승인 후 작성자 merge

`작성자 PR → 다른 팀원 1명 review → 작성자 merge`

- 장점: 빠르고, 초기 maintainer가 병목이 되지 않는다.
- 위험: reviewer가 내용을 보지 않고 승인하면 review가 의례가 된다.

### B. 순번 integrator merge

`작성자 PR → 다른 팀원 review → 이번 주 담당자가 merge`

- 장점: 초보 팀원이 merge를 직접 하지 않아도 되고, 운영 경험을 순환할 수 있다.
- 위험: 순번 담당자가 새 병목이나 실질적인 승인자가 될 수 있다.

### C. 변경 위험도별 두 레인

- 문서: 다른 팀원 1명 review 뒤 작성자 merge
- 코드·workflow·저장소 설정: 다른 팀원 review 뒤 maintainer 또는 담당자 merge

- 장점: 문서는 빠르게, 배포와 설정은 조심스럽게 운영할 수 있다.
- 위험: 어떤 변경이 “설정 변경”인지 경계를 팀이 이해해야 한다.

첫 회의에서는 영구 제도보다 **1주 동안 시험할 기본값 하나**를 고른다. 시험 뒤 실제 마찰을 보고 바꿀 수 있다.

## 5. Notion과 GitHub의 경계

다음 표는 사용자의 제안을 구체화한 **한 가지 배치안**이다. 팀은 GitHub Issues 대신 단순 문서 체크리스트를 쓰거나, Notion을 더 넓게 유지하는 대안도 비교할 수 있다.

| 정보 | 제안 위치 | 이유 |
|---|---|---|
| 최종 문서·회의 결정·코드 | GitHub `main` | 변경 이력과 작성자가 남고 Pages와 연결된다. |
| 작업 질문·할 일 | GitHub Issues | 담당자, 상태, 관련 PR을 연결할 수 있다. |
| 실제 변경 검토 | Pull Request | diff를 놓고 review할 수 있다. |
| 공개 읽기 화면 | GitHub Pages | `main`의 `docs/`를 자동 렌더링한다. |
| 과거 Notion 자료 | archive 또는 읽기 전용 | 계보는 보존하되 새 정본과 충돌하지 않게 한다. |
| 회의 중 함께 보는 칠판 | Notion 등 실시간 공동 화면 | 동시에 적고 가리키는 데 사용하되, 결정은 GitHub에 옮긴다. |

핵심은 “Notion을 절대 쓰지 않는다”보다 **최종 판정이 어디에 남는지 한 곳으로 고정하는 것**이다.

사용자의 현재 제안은 **Notion=실시간 칠판, GitHub=정본**이다. 회의가 끝날 때 Notion의 전 내용을 이관할 필요는 없다. 결정된 것, 남은 질문, 다음 담당자만 Issue·PR·markdown 중 알맞은 곳에 옮기면 된다. Notion 무료 한도로 공동 편집이 막히면 다른 실시간 칠판을 써도 이 경계는 변하지 않는다.

## 6. GitHub가 처음인 팀원의 첫 회차

처음부터 Obsidian, Dataview, CLI를 모두 설치하지 않는다. 첫 회차에는 한 사람이 전부 할 필요가 없다.

1. 작성자는 GitHub 웹에서 작은 markdown을 수정하고 PR을 연다.
2. reviewer는 “무엇이 바뀌었나 / 의도와 맞나 / 공개해도 되나” 세 가지만 보고 의견을 남긴다.
3. merge와 Actions·Pages 확인은 이번 회차 담당자가 함께 보여준다.

PR 설명은 처음에는 `무엇을 바꿨나`와 `왜` 한 줄씩이면 충분하다. Actions가 실패하면 작성자가 혼자 해결하는 규칙부터 만들지 말고, 초기 maintainer나 이번 회차 담당자에게 연결한다.

이 한 바퀴를 함께 본 뒤 필요하면 다음 PR에서 역할을 바꾸고, 로컬 clone·VS Code·Obsidian을 선택한다. 도구 설치는 협업 흐름을 이해하기 위한 선결 조건이 아니다.

## 7. 오늘 30분 회의안

1. **5분 — 실제 사건 확인:** PR은 merge·배포됐지만 메뉴에서 빠졌고, 현재 PR이 자동 발견을 해결 후보로 제안한다는 것을 함께 본다.
2. **5분 — 정본 판정:** GitHub `main`을 최종 정본으로 둘지, Notion은 어디까지 쓸지 정한다.
3. **8분 — review와 merge:** A/B/C 중 1주 시험할 흐름을 고른다.
4. **6분 — 문서 분류:** 새 문서를 후보 아이디어·조사자료·결정 기록 중 어디에 둘지 정한다.
5. **6분 — 다음 한 회차:** 작성자, reviewer, 확인할 작은 PR 하나를 정한다.

아이디어 우승안을 고르는 회의와 GitHub 운영을 정하는 회의는 분리해도 된다. 먼저 새 문서를 쓴 팀원이 이 문서를 후보 아이디어·조사자료·다른 종류 중 무엇으로 의도했는지 말할 기회를 둔다. 그 뒤 게시 과정에서 드러난 문제만 운영 논의의 실제 사례로 사용한다.

### 사용자가 설명할 때의 말 흐름

1. **문제에서 시작:** “Notion 용량 문제도 있고, 최종 문서가 여러 곳에 흩어지면 무엇이 최신인지 모르겠다.”
2. **역할을 한 줄로 분리:** “Notion은 같이 보는 칠판, GitHub `main`은 최종본, Pages는 읽기 화면으로 쓰자.”
3. **실제 사건을 보여줌:** “서진님 문서는 branch→PR→merge→배포까지 됐지만 메뉴 자동화가 없어서 사이트에서 못 찾았다.”
4. **상태 사다리를 설명:** “작업 → remote branch → PR → main → Actions → Pages 순서다. push만으로 main이 바뀌지는 않는다.”
5. **화면 네 곳만 시연:** Code, Pull requests, Files changed/Review, Actions를 보여준다.
6. **팀 판정 세 가지만 받음:** 누가 review하는가, 누가 merge하는가, Notion에서 무엇만 GitHub로 옮기는가.
7. **작은 다음 회차로 끝냄:** 한 명이 작은 문서 PR, 다른 한 명이 review하는 것만 정한다.

branch 전략, Conventional Commits 전체 규격, Obsidian·Dataview 설치, Projects 자동화는 오늘 전부 가르칠 필요가 없다. 필요가 생길 때 다음 층으로 연다.

## 8. 팀 판정 기록

- 1주 merge 실험안: `A / B / C / 다른 안`
- review 최소 조건: `결정 전`
